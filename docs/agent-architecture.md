## 一、这个系统是什么

一个跑在我个人机器上的多 Agent 自动化系统，用来接手那些**重复、耗时、容易漏**的工作：行情监控、数据记录、内容整理、定时提醒、跨会话长期任务。

**我的角色**：我不是从零写了一个 Agent 框架（那是开源项目做的），我做的事情是：

1. **把框架用起来** —— 从 2026-03 就在 OpenClaw 上调 skills 做真实任务（最早的会话记录 2026-03-19 19:14，我让它用 weather skill 规划出行，工具调用链完整可查）
2. **沉淀自己的技能库** —— `skills/` 下 **119 个由我亲手编写并持续维护**的技能
3. **搭调度与投递层** —— **22 个在跑的定时任务**，飞书 / 邮件 / origin 三类通道投递
4. **设计记忆与降级** —— 双存储记忆机制，工具调用失败的分级处理

## 四、三个关键设计

### 1. 技能热插拔

新增一种能力不需要改核心代码，只要在 `skills/` 下建目录、写清触发条件和输入输出契约，系统就能发现并加载它。

**为什么这条重要**：能力扩展成本必须足够低，否则系统会僵化在最初的几个场景里。119 个技能里有相当一部分是后期加的——如果每次都要改核心，早就停摆了。

### 2. 工具调用失败的分级处理

不是"重试三次然后报错"。分三层：

- **可重试**（超时、限流）→ 指数退避
- **需降级**（某工具不可用）→ 切备用路径继续完成任务，并标注降级
- **需人工**（连续失败）→ **主动告警**

**核心原则：不静默失败。** 一个没发出但看起来发出去了的告警，比没有告警更危险。

### 3. 双存储记忆

`state.db`（结构化状态，关系型）+ `memories/`（半结构化记忆条目）。前者管"系统现在是什么状态"，后者管"我之前知道了什么"。

跨会话记忆的意义：长期任务（比如"持续跟踪某类数据并定期汇总"）可以跨越几天、几十次会话继续跑。

## 五、真实事故与恢复

### 10-18 渲染帧并发抢写事故

- **现象**：僵尸进程并发抢写渲染帧，导致输出帧损坏
- **恢复**：`pkill` 清理僵尸进程 → 重渲
- **闭环**：加了 **1830 帧硬校验**，渲染完成后逐帧校验，损坏即失败重试

**这件事的价值不在于"出过事故"，而在于出了事故之后我改了什么。** 一个只会说"我的系统很稳定"的人，说服力远不如一个能讲清楚"我这里出过什么问题、怎么定位、怎么加了校验闭环"的人。
