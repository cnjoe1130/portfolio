## 8.1 多 Agent 系统的结构

### 1）Agent 的真实名字与职责

这台机器上不是"7 个对等 Agent 各司其职"，真实形态是 **1 个主 Agent + 按通道/场景派生的子 Agent + 若干专家 Agent**，且横跨两代框架：

| 名字 | 在哪 | 职责 |
|---|---|---|
| Hermes `default` profile | `~/.hermes/` | 主 Agent：飞书 DM 对话、工具执行、cron 任务会话（盘中/盘后/盘前等 22 个任务都在它的调度器里跑） |
| OpenClaw `main` | `~/.openclaw/agents/main/` | 前代框架主会话（2026-04 起），迁移后留档 |
| `hongli`（弘历） | `~/.openclaw/agents/hongli/` | 玄学派 AI 人设——世界杯"AI 吵个球"栏目的预测角色，也承担公众号发图 |
| `wechat-reader-expert` | `~/.openclaw/agents/` | 微信读书助手（weread）专家 Agent |
| `redsecret-expert` | `~/.openclaw/agents/` | REDSecret 隐写工具专家 Agent |
| `cbcd6328a5c3-im-bot` | `~/.openclaw/agents/` | IM 通道机器人 |
| QClaw 等工作 Agent | 独立环境 | Joe 的多 Agent 并行模式：QClaw 等做研究/调研，本机 Hermes 专注工具角（OCR/视频/食物记录/配置），互通过任务单交接（技能 `cross-environment-outsourcing`、`agent-delegation-specs` 就是为这个写的） |

**诚实声明**：如果简历要写"7 个 Agent"，上表恰好 7 行，但它们是**两代框架 + 一主多辅**的结构，不是一个 orchestrator 下的 7 个对等 worker。面试按上表讲比按"7 个对等"讲更硬。

### 2）skills/ 目录真实结构

本包 `01-agent-system/skills/` 即原样拷贝：99 个目录（119 个亲手创建技能中现存者），每个目录 = `SKILL.md`（frontmatter: name/description + 正文工作流）+ 可选 `references/`（踩坑记录、案例）、`templates/`（HTML/JSON 模板）、`scripts/`（配套代码）。示例：

```
a-share-market-cards/
├── SKILL.md                    # 主工作流：抓取→写卡→截图→发布
├── references/                 # 11 份：wechat-publishing.md、qr-encryption.md、cron-feishu-delivery.md…
├── templates/after-market-card.html
└── SKILL.md.v3.14.bak          # 版本演化痕迹（v3.14→当前）
```

另有 `skills-archive/` 收录 19 个已退役技能——技能有生命周期，退役不等于删除。

### 3）技能热插拔怎么实现

框架侧机制（Hermes 开源，非本人编写）：**零重启、零注册表**。新增一个技能 = 在 `~/.hermes/skills/<name>/` 建目录写 `SKILL.md`；系统在每次会话构建 system prompt 时扫描技能目录，把 `name + description(≤57 字符)` 注入 `<available_skills>` 清单；模型在回复前扫描清单，判定相关就调 `skill_view(name)` 拉全文进上下文。**发现靠语义匹配，加载靠显式调用**，所以"装"就是"建目录"，"卸"就是"挪进 .archive"。

我在这层之上加的做法：agent 完成 5+ 工具调用的复杂任务后，被要求用 `skill_manage` 把工作流沉淀成技能；用技能中发现步骤缺失/命令过时，当场 `patch` 修订。所以我的 119 个技能是**任务驱动的自维护产物**，不是抄来的清单——每个 SKILL.md 里的命令都在本机真跑过。

### 4）跨会话记忆持久化

双存储（文件 + SQLite），职责不同：

- **会话原文**：`state.db`（SQLite，本机约 1.4GB，本包不打包）——`sessions`/`messages` 表 + FTS5 索引（`messages_fts`、`messages_fts_trigram`），检索靠全文索引而非向量库。实测：跨 3 个月前的会话能按关键词捞回。
- **长期记忆**：`memories/MEMORY.md`（我的工作笔记）+ `USER.md`（用户画像），纯文本、`§` 分隔条目，每次会话注入上下文。上限管理：MEMORY 有 2200 字符预算，满了必须合并旧条目——这是**约束驱动的定期压缩**，比无限膨胀的向量库更可控。
- **程序性记忆**：`skills/`（见上）。
- 三层分工的原则：会话=原始档案、记忆=稳定事实、技能=可复用流程。"一周后会过时的东西不进记忆"（写进系统规则的纪律）。

没上向量库是明确的取舍：FTS5 + trigram 中文检索在这个量级（12.9 万条消息）够用，运维成本为零。

### 5）Cron 调度粒度

**每个任务独立 cron 表达式**，统一调度器执行（框架侧 APScheduler 式）。本包 `cron/jobs.json` 22 个任务全带原始表达式，粒度从 `13 7 * * 1-5`（工作日 7:13）到 `20m`（每 20 分钟看门狗）都有。两类任务体：`no_agent`（直接跑 `scripts/*.py`，不付 token，如黄金价位监控）与 `llm`（整段 prompt 交给 agent 会话，如 A股盘后分析）。**能用脚本的绝不进 LLM**——22 个任务里 6 个是纯脚本。

### 6）告警走哪个通道

- **任务级**：cron 失败 → `agent.log` 记 ERROR（样本见 `logs/sample-alert-504.log`，9-24 连环 504）；任务成功产出走 `origin` 投递 = 飞书 DM 卡片（本会话即通道实证），A股卡同时走公众号发布。
- **哨兵级**：黄金监控（每 3 小时比对阈值，触发才推送——**无事不打扰**是设计点）、午餐/晚餐提醒、邮箱扫描告警。
- 邮件通道（`每日邮箱扫描` 9:00 + agently-cli）真实在跑，用于非即时场景。
- 诚实边界：**框架没有统一的"告警中心"**；失败目前靠日志 + 次日会话抽查（memory health check 任务）兜底。这是待改进项之一。

### 7）工具调用失败的完整处理链路

真实分层（均可在 `logs/` 样本对应）：

1. **传输层重试**：API 429/超时 → 固定 3 次重试 + 指数退避（日志实证 `attempt 1/3 → 2.5s → attempt 2/3 → 4.5s`，见 `sample-retry-429.log`）。
2. **工具层回传**：工具报错**不吞异常**，把错误原文作为 tool result 交还模型，由模型决定换参数重试/换工具/放弃（`terminal` 返回 `{"error": "..."}` 即此层）。
3. **技能层降级**：写技能时显式定义降级路径。例：行情 API 失败→用缓存数据+模板化简报并在产物标注降级；vision QC 服务 503→退化为按用户文本描述提取，不阻塞主流程（character-poster-generation 里有明文）。
4. **任务层放弃并告警**：重试耗尽 → cron 标记 job failed，错误进日志，下次调度照跑（不因一次失败停摆）。504 高峰这类系统性故障 → 衍生出永久对策：`cron504看门狗` 任务 + 504 时段选模避让策略（沉淀进 hermes-session-management 技能）。

### 8）多通道推送的"多"体现在哪

**一个产物最多同时进 4 个出口**：A股盘后图卡 = ① 飞书 DM（origin 投递，Joe 即时看）→ ② 微信公众号（发布管线）→ ③ 本地台账（`cron/output/` 归档）→ ④ 小红书内容库（平台策略：小红书当增长引擎、公众号当沉淀池）。投递目标在 jobs.json 里按任务声明（`origin`/`local`/`email`/`feishu`），不是硬编码——这是"同一任务多投"的配置层证据。

### 9）跑崩过吗？最严重的一次

**10-18 视频渲染并发抢写事故**（完整三份日志在本包 `logs/incident-1018-*.log`）：HyperFrames 渲染 1830 帧成片时，前序被中断的渲染进程没退干净（僵尸进程），新进程与僵尸并发写同一帧序列 → 帧数校验 `assert total==1830` 两次失败（1710、1785——不是崩溃而是**被硬校验拦住**）。处置：`pkill` 清场→重渲→1830 帧全量校验通过才交付成片。

这条的价值：**缺帧成片比渲染失败危险得多**，帧数断言是故意设计的"宁可失败不可缺帧"闸门，日志三连（fail 1710 → fail 1785 → pass 1830）证明闸门真的兜住了。

### 10）现在重写一遍，最想改的设计

1. **cron 加交易日历**：节假日休市仍触发任务（10-02 假期空跑），目前靠"哨兵输出 [SILENT]"兜底——数据层判定停市（涨停池 total=0 + 无新闻 + 指数陈旧）是补丁不是方案。
2. **compaction 策略**：长任务上下文超限是当前最大成本项（本包制作过程自己就超限过一次）。想改成"结论+数字+文件路径"结构化摘要优先，而非全文压缩——摘要丢掉的恰恰是要用的数字。
3. 统一告警出口（见第 6 条的诚实边界）。

## 8.2 499/超时故障：排查方法论（框架，不含具体实验数据）

### 现象
LLM 中转服务间歇性返回 499 与超时，影响定时任务产出。

### 排查框架
不猜。把可能原因拆成三项，逐项设计**可证伪**的对照实验：

1. **推理模型时延变长？** → 对照：同模型直连官方端点、绕过中转，比首 token 延迟基线。
2. **中转协议/端点问题？** → 对照：多个中转服务商跑同一请求、同 prompt 对比（本机留有工具：`scripts/provider-verify.py`、技能 `llm-provider-audit`/`llm-provider-verification` 即这轮沉淀——审计中转是否"套壳"）。
3. **并发限流？** → 实验：观察 499 出现与自身并发数的相关性，降并发重试验证。

### 结论与修复
定位到**并发限流**。修复分三层：退避重试 → 切备用中转并降并发 → 降级路径（缓存数据 + 模板化简报）继续完成任务并在产物上标注降级。

### 沉淀
这条路径固化进系统的工具调用层（3 次重试/指数退避/错误回传模型），成为所有技能共用的失败处理策略；衍生出 `cron504看门狗` 常驻任务。**具体实验数据与结论细节以本人复述为准**——本节只保证方法论框架可自证（上面引用的脚本和技能文件都在包里）。

## 8.3 随驾 SuiJia 的隐私取舍

（据 `04-suijia/README.md`"怎么工作"与"隐私边界"节 + 三代演化史，均为仓库原文可核对）

1. **实时语音转写**：上游一代（jev-jarvis 单条复制）→ 二代（截图分享 OCR）→ 三代（随驾，ReplayKit 广播+本机 Vision OCR）。放弃"全自动实时回话"是核心决策：链路图画得很清楚——帧流→去重→OCR→说话人归属→App Group 全程不出网，**只在用户点「分析」那一刻才外发文本**。不做"AI 替你把话说完"的实时接管。
2. **"打断对话"的判断来源**：产品自我定位"你聊天，它在旁边看着，回话前递条子"——副驾不能抢方向盘。复制单条丢上下文是二代痛点，但补上下文不等于替用户发言；候选话术必须**点选**才填入输入框，发送键永远在人手里。
3. **「仅主动点击才外发」牺牲了什么**：牺牲即时性（候选不是自动出现的）；牺牲一部分准确率场景（语音消息、图片消息进不了 OCR，广播只含视频流——README 诚实条款自己承认）；牺牲体验流畅度（多一次点击）。换来的是：无自建服务器、不落盘、不进日志、API Key 只存本机 App Group。
4. **商业化怎么改**：现设计本来就允许用户自带任意 OpenAI 兼容端点（DeepSeek/GLM/OpenRouter）——即"接入云端模型"已经是现状，但云是**用户自己的云**（用户配置的 Key 计费到用户账上）。商业化要动的是默认端点托管，那时必须保留 BYOK 路径与"点击才外发"约束作为信任底线，否则产品卖点（隐私）就没了。这一点 v0.1 源码已把生成层做成可插拔配置，架构上留了口子。

## 8.4 互动叙事引擎的角色一致性

（据技能 `character-poster-generation`、`dreamloom-engine-adaptation`、`interactive-fiction-conversion` 原文，日期戳为实测记录）

1. **漂移的具体表现**：同一角色跨镜头——脸型/单双眼皮变化、发型位置翻转（辫子从左肩跑到右肩）、服装件数与滚边纹样走样、标志性道具丢失或换位（剑拿反、发簪消失）。不是"画得不像"，是**同一人不同图之间不一致**，这在 15+ 节点的分支游戏里成片出现时穿帮感极强。
2. **试过的方案与最终锁定**（演进链，非一步到位）：
   - 纯提示词描述角色外貌 → 单图可用，跨图必漂。弃。
   - **参考图条件生成（`--ref`）+ 提示词逐件复述** → 主力方案。
   - LoRA 微调：未走——生图 API 服务（A2A/Agnes）不支持自定义训练，且 100+ 角色的训练成本与一致性收益不匹配。这是明确的方案排除记录。
   - 最终定型为五步锁：① vision 供图**元素清单化**（脸/发型位置/服装逐件/道具/光线，逐项列）→ ② **锁死项 vs 可调项分列**给用户拍板（用户说"严格按供图"时锁死项一字不改）→ ③ 英文 prompt 逐件复述锁死项（底层模型英文准）→ ④ 生成 → ⑤ **验收三查**：脸→服装→左右位置。
3. **实现原理与成本**：原理=参考图做视觉条件 + 文字清单做特征注入，双通道冗余——图定"长相"，逐件复述定"穿法/位置"（左肩/右肩这种镜像错误就是靠文字锁位修的）。成本：单图秒级到 1 分钟（high quality 档），验收三查靠 vision 模型自动过 + 人工终审（Joe 拍板审美，AI QC 分只是参考）。配套的时间线一致性：《生吞》改编实测出**三代头像**（少年 1999/青年 2003/中年 2019）——同一角色跨时间线漂移靠"骨架阶段就规划每角色几版头像"解决，不是生成端解决。
4. **一致性之外的美术问题**：风格统一（同批图的光线/色调分级——模板里 `soft matte cinematic lighting`、`warm beige color grading` 写死）；排版位固定（右侧 CITY 字样区）；个人符号与场景共存（蝴蝶发簪写进双曝光场景层与城市剪影融合，第 4 张验证）；深色模式/UI 混入过滤。
5. **工业化一次出 100 节点撑不撑得住**：撑得住，因为管线已经是批量的——`build_single.py` 自动内嵌 `avatars/thumb/` 144px 缩略图（31-38KB/张，单机版 ~1MB）、批量生成脚本按 `(角色id, prompt)` 列表循环、生成前自动备份 avatars 目录。真正的瓶颈不在生成而在**验收**：100 节点的三查若全人工不可扩展，现有解法是 vision 预筛 + 人工只看可疑件 + 失败件登记不中断、交付后统一返修（这条流程已写进美术外包规范）。

## 8.5 三个 0→1 项目的取舍复盘

（据各项目仓库/技能内的日期戳决策记录，标注可核对处）

### 吃了么

1. **最难的判断**：推荐边界——"习惯内推荐"引擎被约束成**只做自我对比**（推荐候选必须从 Joe 自己的历史账本里检索，不引入外部"健康食谱"评判他）。这是对的位置：营养工具最容易做成爹味说教，砍掉"标准饮食"维度后产品变成 Si 外包训练器（记账换算存档，留给用户的只有回忆报数）。
2. **错误的决定**：食物库早期把整盒装标签按 per-100g 存（泰森 168g/盒 886kJ 存成单位热量），宏量营养素系统性偏差；周复盘"油是唯一变量"的规律差点被脏数据掩盖。后按"标签按份直读制"重建，并沉淀成数据规范技能。
3. **重来第一步改什么**：第一天就按真实数据结构写脱敏/校验脚本（本次素材打包又踩一遍：个人字段散布在每日账本不在本体——需求文档的字段清单空对空，脚本必须按实际 schema 写）。

### 随驾 SuiJia

1. **最难的判断**：做"递条子的副驾"而不是"替你说话的自动回复"。技术上全自动链路已经画得通（帧流→OCR→外发→回填），产品上停手——这个自我设限就是产品。
2. **现在回看错的决定**：v0.1 把语音/图片消息留空（诚实条款自认）——恰恰是微信聊天最高频的输入类型，导致"读整场对话"的卖点在场景上打折。
3. **重来第一步**：fork 前先跑真机原型验证 ReplayKit 在微信前台的存活（10-02 已装双 App、7 天重签节奏已成型）——三代演化中一代二代的弯路（单条复制、截图分享）本质是没先验证"上下文"值多少。

### 互动叙事引擎

1. **最难的判断**：改编密度——长篇（几十万字）到分支 JSON，逐章全覆盖会做成电子书，只留主线会失真。定案"先骨架后血肉"（2026-08-04 记录在案）：结构/流向先全量拍定并给用户对照表，文本后填，视觉最后（防返工）。
2. **错的决定**：《生吞》首轮只规划了 1999-2003 两版头像，漏了 2019 中年线——后期返工生成。教训固化成"三时间线意识"检查项写进技能。
3. **重来第一步**：第一天就建"逐章覆盖审计"（现在有 novel-fidelity-audit 技能），否则长改编最怕的不是单点质量而是"结局偏离原著"的结构性漏。
