REDSecret · AI Agent 隐写通信工具

在线可玩已开源
纯浏览器端 JS（零依赖、零服务器）· MIT License · 2026.05-06
针对「Agent 间安全传递结构化信息」与社交隐蔽表达需求，设计并实现三种隐写方案：LSB 像素隐写（3 通道 RGB 逐位交错，像素级不可见）、QR 角标隐写（抗 JPEG 与社交平台有损压缩）、零宽字符隐写（Unicode 零宽字符藏于普通文字，肉眼完全不可见）。自定义载荷格式（magic header + 版本 + 长度 + 校验和），XOR 流加密。
外部只依赖 qrcode 与 jsQR 两个通用库——隐写与加密逻辑全部自研：自定义 magic header + 3 通道交错 LSB 提取 + 4 变体零宽映射，这套组合在公开仓库里没有第二份实现。
一次主动的重写：它最早是 Python 版，后来我重写成纯浏览器版（commit 里能看到 chore: remove legacy Python scripts (now browser-only)）——浏览器端零依赖、零服务器、数据不上传，才符合隐私定位。仓库 15 个 commit 全是我一个人，无 fork。
硬指标：经 24+ 种攻击算法测试未被破解；适配微信朋友圈/小红书/飞书的图片压缩场景，解码成功率 95%+。
像素隐写对比图为本机引擎真实生成，实测 diff 均值 0.0012/通道；payload 区约占 1/3 行，不宣称全图逐像素无差。
→ 在线体验 Demo（浏览器端运行，数据不上传）

我的资产层：119 个技能 + 22 个在跑任务

运行中2026-03 起
框架为开源项目（Hermes Agent / OpenClaw）· 我的部分是技能层与编排层
先说清楚边界：Agent 框架本身是开源项目，不是我写的。我做的是四件事——① 从 2026-03 就在上面调 skills 跑真实任务② 沉淀 119 个亲手编写并持续维护的技能（provenance 可查）③ 搭 22 个在跑的定时任务与多出口投递④ 设计分层记忆与工具失败的分级降级。
技能库共 283 个，其中 164 个为导入/外部来源。我把 119/283 这个比例直接写出来——分清哪些是我写的、哪些是导入的，本身就是工程判断的一部分，比声称"我写了 283 个"更可信。
关于"7 个 Agent"这个说法——我做过一个不准确的表述。它不是"7 个对等 Agent 各司其职"，真实结构是两代框架 + 一主多辅：主 Agent 承担对话与工具执行、按通道/场景派生子 Agent，另有若干专家 Agent（如 REDSecret 隐写、微信读书），跨设备还有研究型 Agent 通过任务单交接。我按真实结构讲，而不是按一个好听但站不住的数字讲。
能力实现方式
调度22 个在跑，每个任务独立 cron 表达式（13 7 * * 1-5 到 20m 看门狗）；任务体分 no_agent（纯脚本，不付 token）与 llm（agent 会话）两类
扩展技能热插拔——零重启、零注册表：建目录写 SKILL.md 即被发现，"装"就是"建目录"，"卸"就是"挪进 archive"

记忆三层：会话原文 state.db（SQLite + FTS5 全文索引，12.9 万条消息）＋ 长期记忆 MEMORY.md（2200 字符预算，约束驱动压缩）＋ 程序性记忆 skills/
韧性四层：传输层重试（429/超时，3 次指数退避）→ 工具层错误不吞、原文回传模型 → 技能层显式降级路径 → 任务层放弃并告警（不因一次失败停摆）

一次真实事故，以及我改了什么

10-18 渲染帧并发抢写：渲染任务产出异常，输出帧损坏。排查时先怀疑渲染逻辑本身（参数、素材、时间线对齐）——单独跑正常，排除；再怀疑资源不足——监控显示有余量，排除；回头看进程表发现僵尸进程残留并持有帧文件写句柄，定位到并发抢写。

恢复：pkill 清理僵尸进程后重渲。但恢复不是终点——我随后加了 1830 帧硬校验：渲染完成后逐帧校验，任意一帧损坏即判定失败并重试。

为什么讲事故而不是讲"我的系统很稳定"：面试官判断工程水平，看的不是"你出过事故吗"，而是"出了事故之后你改了什么"。一个能说清楚"这里出过什么问题、怎么定位的、怎么加了校验闭环"的人，比一个声称没问题的人可信得多。
另一类失败：工具调用失败的分级处理。AI 流程里单次调用失败是常态（网络抖动、限流、上下文超长、模型抽风）。如果产品没设计好这一层，用户感知到的就是"这个 AI 时好时坏"——而这恰恰是很多 AI 产品失败的原因：不是模型不行，是没处理失败。

03

产品判断

工具谁都能用。我更想说明的是我在什么地方做了判断、为什么这样判断——这三件事是我这一年最核心的学习。

① 副驾产品：真问题不是「没有回复」，是「打断」

起点是一句用户抱怨：「复制粘贴很打断对话」。当时最直觉的方案是做成实时语音转写 + 自动回复。但我判断真正的痛点是打断而不是缺失——用户要的是不被打扰地继续对话。

所以我选择让识别全程留在本机（Vision OCR 本地推理），并且只在用户主动点击时才触发分析。这让隐私从「一个加分项」变成了「这个产品能不能被用」的前提。代价是响应变慢了，我接受这个代价。

② 内容栏目：用产品结构解决合规问题，而不是加免责声明

「AI 预测比赛结果」天然存在博彩合规风险。加免责声明是最省事的做法，但会持续消耗用户的信任。我改成两个 AI 给出不同结论的对抗结构——「东方玄学」对「西方数据」——冲突本身就是内容，而双 AI 天然不导向任何单一下注结果。

合规从「事后修补」变成了「产品结构的一部分」。这让我意识到：很多风险可以在设计阶段就消解掉，而不是在上线后打补丁。

③ 故障排查：把猜测换成可证伪的对照实验

LLM 中转服务间歇性返回 499 / 超时。我不猜，而是把可能原因拆成三项，各自设计一个能推翻自己的对照实验：① 同模型直连官方端点、绕过中转，比首 token 延迟基线 → 证伪"模型时延变长"；② 多个中转服务商跑同一请求同一 prompt 对比 → 排除"协议/端点共性问题"；③ 观察 499 出现与自身并发数的相关性，降并发重试 → 定位到并发限流。

修复分三层：退避重试 → 切备用中转并降并发 → 降级路径（缓存数据 + 模板化简报）继续完成任务并在产物标注降级。这条路径后来固化进系统工具调用层，成为所有技能共用的失败处理策略。

做 AI 产品的门槛，一半在「懂业务」，另一半在「知道模型和基础设施的真实边界在哪」。后者不能靠看文章，只能靠动手踩过。

业务背景

我不认为懂业务和懂 AI 是两件事。以下是我在业务侧的真实积累——它决定了我知道哪些环节值得被 AI 改造。

经历结果
佳格投资 · 京东运营
2022.01-2025.03		连续 3 年店铺全年 GMV 突破 2 亿，年均达成率 110%+，领跑公司同品类团队；葵花籽油类目销售第一，市场份额 15%+；核心 SKU 转化率 +12%，大促 ROI 同比 +25%
森中网络 · 售后客服主管
2020.04-2021.12		统筹天猫/抖店/拼多多/快手/考拉/小红书多平台售后；主导话术机器人关键词库与应答逻辑优化，自动化回复准确率 75%→92%，减少 30% 人工咨询量；响应 4h→1.5h，解决率 98%，客诉率 -30%，DSR 4.9+
上海四衡 · 跨境电商运营
2019.08-2020.03		滞销率 -20%，周转天数 -5 天；主图与详情页优化点击率 +15%、转化率 +8%
为什么这段经历对 AI 产品岗有用：客服那三年让我知道 AI 智能客服真正的瓶颈不在模型，在知识组织的颗粒度和异常路径的处理；京东那三年让我知道一个业务环节值不值得被 AI 改造，取决于它的频次、标准化程度和错误成本——这三点决定了 ROI。这两件事是很多 AI 产品候选人缺的，因为它需要真的做过业务、真的踩过坑。
